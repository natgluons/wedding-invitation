# Hanfu Letter Invitation: Agent-Ready Asset Kit

**Purpose:** A composable, mobile-first digital wedding invitation inspired by a Chinese historical-romance drama and the act of opening a personal letter. Decorative assets are supplied independently so your coding agent can make actual UI with editable copy and interactions. **These are not screenshots cut into buttons.**

## Quick start

Open `index.html` in a browser (or serve the repo root with any static server). Tap the wax seal / **Open the letter** button. The envelope has a separately animated flap, front pocket, emerging letter, wax seal, and tassel. The invitation then shows a couple hero, event details, story, RSVP, gift details and closing. The background song starts when the letter is opened, and the note button in the bottom-right pauses or resumes it.

For best results, from the repo root run: `python -m http.server 8000` and open `http://localhost:8000/`.

### Personalised invitation links

The live RSVP flow uses a private invitation code in the `Guests` sheet. Its generated link includes both a code and an encoded display name. Use `?code=YOURCODE&name=Richard%20%26%20Kristy`; `name` is provisional while the page verifies the code; the server's current name is authoritative, and URL names or seat parameters never grant access or allowances. The greeting uses the sheet Name exactly, without adding “& Guests” or a reserved-places line.

Name-only links below are supported for preview or legacy use when the backend is not configured. They do not authenticate a live RSVP:

- `/alice` → cover shows **Dear alice,** and the envelope says **For alice**.
- `/alice?plus=0` → preview seat allowance of 1; the name is unchanged
- `/alice?guests=3` → preview seat allowance of 3; the name is unchanged
- `?name=John` or `?to=John` also work, with the same `plus` / `guests` options.
- `?lang=id` or `?lang=en` switches the whole invitation language (also `/id` and `/en`). Domestic and International transfer tabs are independent of the language, with Domestic selected by default.

Path links (`/alice`) keep the URL clean. They need a host that serves `index.html` for unknown paths: `_redirects` covers Netlify, and `404.html` makes GitHub Pages forward `/alice` to `index.html?name=alice`. On GitHub Pages the address changes after the forward, though the invitation still greets Alice.

Names are rendered with `textContent`, so names from a URL cannot inject HTML. When the backend is connected, only a verified code can reveal a saved response or submit changes.

### Generating one link per guest

Put your guest list in `guests.csv` (copy `guests.example.csv`):

```csv
name,seats
John Tan,2
Alice Wijaya,1
The Wong Family,4
```

Then run:

```powershell
node tools/generate-links.js --base https://yourname.github.io/wedding-invitation/
```

The base URL defaults to `siteUrl` in `config.js`. Add `--lang id` or `--lang en` to put the language in every generated link. The script writes:

- `guest-links.csv`: guest name, seats, and full link (opens cleanly in Excel/Sheets)
- `guest-links.html`: a preview table with a copy button per guest, handy for WhatsApp

This legacy helper does not create authenticated invitation codes and should be treated as a preview utility. Live links should be generated by the `Guests` sheet formula below. Duplicate names are skipped, names with commas/quotes/`&` are encoded correctly, and seat counts are clamped to 1–4.

## RSVP backend (Google Sheets)

The form in `index.html` posts to a Google Apps Script Web App, which keeps one current response per invitation and appends accepted snapshots to history. Nothing is sent until you complete this setup.

1. Create a new Google Sheet and copy the long ID from its URL:
   `https://docs.google.com/spreadsheets/d/`**`THIS_PART`**`/edit`
2. Open <https://script.google.com> → **New project**, replace the default code with `rsvp-backend/Code.gs`.
3. Paste the sheet ID into `const SHEET_ID = '...'` at the top of `Code.gs`.
4. Run the `setup` function once (choose the function in the toolbar → **Run**) and approve the permission prompt. This creates or migrates the `Guests`, `Settings`, `RSVP`, `RSVP History`, and `Wishes` tabs. Existing data and header columns are preserved; missing schema columns are appended.
5. **Deploy → New deployment → Web app**:
   - Description: `RSVP`
   - Execute as: **Me**
   - Who has access: **Anyone**
6. Copy the deployment URL that ends in `/exec` and paste it into `rsvpEndpoint` in `config.js`:

```js
window.WEDDING_CONFIG = {
  rsvpEndpoint: 'https://script.google.com/macros/s/AKfy.../exec',
  siteUrl: 'https://yourname.github.io/wedding-invitation/',
  contactWhatsApp: '6281234567890'
};
```

`RSVP` is the current response per invitation code. `RSVP History` is append-only and records every accepted create/update snapshot, server timestamp (Asia/Jakarta), invitation code, request ID, action, attendance, event, guest count, private note, invited name, and page. The server writes history first, then updates the current response projection. A retry with the same request ID is durably idempotent; if a write stopped after the history append, retrying repairs the current row. `Wishes` remains the separate public Words of Love feed. Guest lookup returns only the response for the verified, non-revoked invitation code.

On verification, a returning guest sees a compact saved response and can choose **Edit response**. The form is prefilled; **Cancel** restores the saved values. Successful saves return to the summary. Drafts remain in the form after a failed save. RSVP responses are not restored from browser storage. The RSVP form collects only attendance, selected events and party size; wishes have their own editor alongside the public feed.

If the request fails, the form offers a WhatsApp fallback when `contactWhatsApp` is set. If `rsvpEndpoint` is blank the form stays in preview mode and tells you so.

RSVP submission reads the backend result. If CORS prevents reading the POST response, it checks a JSONP receipt using the same request ID; an opaque response alone never means success.

## Guestbook (Words of Love)

The **Words of Love** section above the closing screen lets guests leave a wish. Each verified invitation can create one wish and edit it later. Wishes are stored in the `Wishes` tab and shown newest first, without pagination or an arbitrary message limit.

- A wish is sent with the same `rsvpEndpoint`; no extra configuration is needed.
- Apps Script cannot return CORS headers reliably, so the page reads wishes with JSONP (`?action=wishes&callback=...`). The backend supports this automatically.
- To remove an inappropriate wish, delete its row in the `Wishes` tab.
- Wishes require a verified invitation code. The displayed name comes from Guests and cannot be changed in the wish form.
- Returning guests see their saved wish, with Edit and Cancel controls. Failed saves retain the draft.
- A successful save includes the moderated feed, avoiding a second API request.
- No wish is saved when the backend is unconfigured.
- If you change `Code.gs`, update the deployment: **Manage deployments → edit the existing deployment → Version: New version → Deploy**.

## Desktop and motion

The invitation is one page at every width:

- **Below 700px:** the original single-column mobile layout.
- **700–959px:** a wider single column (up to 720px) with paper frames.
- **960px and above:** a wide editorial layout (up to 1240px): the opening cover splits into wording and envelope, the hero becomes photograph plus copy, details and gift cards sit in two columns, story becomes photograph plus timeline, and RSVP and the guestbook become copy plus form.
- **1300px and above:** the floating music button aligns with the invitation edge.

Opening sequence: seal fades → flap folds → letter rises → the cover crossfades into the invitation while the hero settles. It finishes in about 2 seconds. **Skip the opening**, Escape, and `prefers-reduced-motion` all reveal the invitation immediately.

While reading, headings, detail rows, story milestones and cards fade up once as they enter view. Content is visible without JavaScript; only `.motion-ready` hides items while waiting. Motion never moves text after it has been read, and forms never animate while focused.

The header links to the existing sections. No additional pages or sections were added.

## Core interaction sequence

1. **Sealed:** Envelope is composed from back, paper, front, flap, string, wax seal, tassel.
2. **Unseal:** Seal and string fade, flap rotates over the top edge.
3. **Unfold:** Paper lifts out from behind envelope pocket.
4. **Reveal:** Enter the full invitation with an unobstructed photo, then details and RSVP.

The opening crossfades into the invitation instead of unmounting the cover abruptly, and the whole sequence can be skipped. Section reveals are one-time and use `IntersectionObserver`; there is no animation library and no scroll hijacking.

## Manual invitation whitelist

Paste the latest `rsvp-backend/Code.gs` into the existing Apps Script project, save, run `setup()` once, then open **Deploy → Manage deployments → Edit**, select **New version**, and deploy. Setup migrates legacy Active flags to Revoke. Guest codes and invitation-link formulas are managed entirely in the sheet; setup never generates or rewrites them. Existing columns, custom columns, and valid codes are preserved.

Guests columns: **Name | Max guests | Revoke | Code | Invitation link**.

- Enter one party per row. Max guests includes the named guest (integer 1–100).
- Revoke blank or FALSE allows RSVP; TRUE blocks it.
- Generate a code in D2 with `=BASE(RANDBETWEEN(0,60466175),36,5)&BASE(RANDBETWEEN(0,60466175),36,5)`. Fill down, then immediately copy the codes and **Paste special → Values only** in the same cells before sharing links, so recalculation cannot change them. Codes must be unique; duplicate codes are rejected. Codes may use 8–64 alphanumeric characters; this formula produces ten base-36 characters. Existing hexadecimal codes still work.
- E2: `=IF(OR(D2="",Settings!$B$2=""),"",REGEXREPLACE(Settings!$B$2,"[?#].*$","")&"?code="&ENCODEURL(D2)&"&name="&ENCODEURL(A2))`. Fill down.
- Set the domain in **Settings!B2**; full links update immediately.

The site looks up the code in this private sheet, fills the authoritative name, restores only that code's current response, and limits the count dropdown. The server independently verifies the code, revocation, party size, attendance, and event. Resubmissions update by invitation code; different parties with identical names remain separate. Keep the sheet private. A link lets its holder respond for that party. Legacy RSVP event labels are mapped to current event keys when a response is restored.

If you maintain the link formula manually, use this in the **Invitation link** cell on row 2 and fill down:

```gs
=IF(OR(D2="",Settings!$B$2=""),"",REGEXREPLACE(Settings!$B$2,"[?#].*$","")&"?code="&ENCODEURL(D2)&"&name="&ENCODEURL(A2))
```

The Wishes tab has **Submitted at | Name | Message | Hide | Guest code | Request ID**. Setup appends missing columns without deleting existing messages. Guest code associates a wish with an invitation; never publish this column. Existing unlinked wishes remain visible, but are not assigned to a guest by name. To make an old wish editable, manually enter the appropriate invitation code on its row (one row per code).

The RSVP form no longer asks for a private note. Historical Message values remain stored privately and are not published as wishes.

The Wishes tab has **Hide** in column D. Blank or FALSE displays the wish; TRUE excludes it from the public feed. Editing a wish preserves its Hide flag. Reload the page after changing moderation flags. With a backend configured, the browser displays only the server's moderated wish list, not older browser-local copies.

Run `node tests/guest-whitelist.cjs` to check whitelist validation, private response lookup, history audit/idempotency/recovery, and wish visibility.

Guest lookup uses header names, so you may insert custom columns or reorder Guests columns. Keep the required header names unchanged: Name, Max guests, Revoke, Code, Invitation link. Setup appends missing schema columns without removing your custom columns or codes, and does not modify invitation-link cells.

## Sheet-controlled gift options

After pasting the updated `rsvp-backend/Code.gs`, run `setup()` once and redeploy the **existing** web app to a new version. Setup creates the `Gifts` tab with clearly labelled BCA, Jago, international bank transfer, PayPal, Ethereum, Base, Solana, Tron, and Bitcoin example rows. Copy/paste-ready examples are in `rsvp-backend/gifts.example.tsv`. These use `YOUR_...` placeholders for preview. Copy buttons work for placeholder values too; replace Account with real receiving details before sharing. It preserves existing Gifts rows and all guest codes and invitation-link formulas. No real receiving details are prefilled. Rerunning setup fills only blank Account cells on recognized starter rows, preserving existing details and Hide flags. Previously hidden crypto rows stay hidden until you set Hide to FALSE.

The Gifts headers are:

**ID | Group | Method | Label | Network | Account | Account name | Details | Link | Memo | Hide | SWIFT / BIC | Bank address**

| Column | Enter |
| --- | --- |
| ID | Unique stable ID, e.g. `bca`, `paypal`, `crypto-base`. Letters, digits, `_`, and `-` only. |
| Group | `domestic` for BCA/Jago; `international` for Bank transfer/PayPal/Crypto. |
| Method | `bca`, `jago`, `bank` (international bank transfer), `paypal`, or `crypto`. |
| Label | Display title, e.g. Bank Jago. For multiple bank accounts, use distinct labels. |
| Network | Crypto network, e.g. Base or Solana. Leave blank for banks/PayPal. |
| Account | Bank account number, PayPal email, or receiving wallet address. Format this column as **Plain text** to preserve leading zeros and long numbers. |
| Account name | Recipient's name; optional. |
| Details | Optional additional transfer instructions; displayed and copyable. |
| Link | Optional full `https://` payment link, e.g. your PayPal.me URL. Displayed with Copy and Open controls. |
| Memo | Optional required memo/tag; leave blank when not needed. |
| Hide | `TRUE` hides this row; blank or `FALSE` allows it. |
| SWIFT / BIC | International bank routing code; displayed with Copy. |
| Bank address | International bank address; displayed with Copy. |

Fill the account details, then set Hide to FALSE for the rows you want to offer. Bank methods require an account number. PayPal requires an email/account or HTTPS link. Crypto requires a network and receiving address; no token restriction is displayed. Enter each network's receiving address independently. A method with no visible, complete rows disappears; if a group has no methods its tab disappears, and if all options are hidden the section displays a details-coming-soon message.

Methods are ordered BCA/Jago and Bank transfer/PayPal/Crypto, with Domestic selected by default when available. Accounts within each method follow sheet order. Multiple Crypto rows become a network selector. Every displayed transfer value has a copy button. Gifts arrive with the authenticated invitation lookup, without a separate fetch. The frontend never receives hidden/incomplete rows or unrelated custom columns. Changes take effect on reload without another deployment. Schema/code changes still require redeployment.

The former static BCA/SWIFT details are now the international `bank` method. Setup appends missing default example rows, including international-bank. Keep payment details in Gifts rather than editing HTML. The sheet remains private, but enabled gift details are shown to verified invitees, so only enter information intended for those guests.

Invitation lookup uses one JSONP request for Apps Script. It fetches the verified guest, saved RSVP, own wish, and gift configuration together. Ordinary RSVP reads skip the write lock; history recovery rechecks data under a lock only when needed. The spreadsheet handle is reused within each backend execution. Copy controls are icon-only, with accessible labels and a checkmark after successful copying.
